ECCEZIONE CONTROLLATA — APP-FACTORY-CORE

`riccardopinato/App-Factory-Core` è il repository di configurazione centrale

======================================================================
3. STACK STANDARD
======================================================================

FLUTTER / DART = default per nuove app Android/iOS.

Kotlin + Jetpack Compose:
- mantenere per progetti nativi già avviati;
- usare quando capability Android specifiche rendono il native path più semplice
  e affidabile;
- non riscrivere in Flutter un progetto valido senza beneficio concreto.

Flutter Web:
- fornire Web Preview/deploy quando tecnicamente possibile;
- il Web può verificare UI, navigazione, responsive, localizzazione e logica
  condivisa;
- il Web NON certifica capability native Android/iOS.

======================================================================
4. ASSEMBLY FIRST — NUOVA REGOLA CENTRALE
======================================================================

Ogni nuova app deve essere trattata come composizione di moduli, non come
progetto da reinventare.

Sequenza standard:

PRODUCT IDEA
-> PRODUCT BIBLE MINIMA
-> APP BOOTSTRAP MANIFEST
-> GOLDEN SELECTION
-> DONOR / OSS DELTA SOLO SE SERVE
-> DOMAIN IMPLEMENTATION
-> QA / EVIDENCE
-> RELEASE

Applicare:
GOLDEN_APP_BOOTSTRAP_FLUTTER_v1_DRAFT.txt

Il bootstrap deve almeno fissare:
- APP_NAME;
- PACKAGE_NAME / BUNDLE_ID;
- versioning iniziale;
- target platforms;
- localizzazione;
- theme/brand seed;
- app icon;
- auth requirement;
- persistence choice;
- backup requirement;
- notifications requirement;
- premium/ads requirement;
- Web Preview boundary;
- selected Golden modules;
- native capability requirements.

======================================================================
5. ICON FIRST
======================================================================

Ogni nuova app deve avere un'icona production-intent dal primo bootstrap.
Non lasciare Flutter/default/placeholder icon fino alla fine del progetto.

Applicare:
GOLDEN_APP_ICON_BRANDING_FLUTTER_v1_DRAFT.txt

L'icona deve:
- comunicare il dominio/funzione rapidamente;
- essere riconoscibile a dimensioni reali;
- essere moderna e commercialmente attraente;
- non apparire come clipart o generazione AI non rifinita;
- essere distinta dai competitor senza copiarli;
- avere Android adaptive icon;
- prevedere monochrome/themed asset quando pertinente;
- avere iOS/Web assets quando target.

ICON CREATED != ICON WIRED != PHYSICAL LAUNCHER VERIFIED.

======================================================================
6. PRODUCT BIBLE / RULE ZERO / SCOPE
======================================================================

PRODUCT BIBLE = source of product truth.
Definisce:
- problema;
- target;
- promessa;
- MVP;
- esclusioni;
- privacy;
- Free/Premium;
- UX;
- feature approvate.

RULE ZERO — PRODUCT FRICTION REDUCTION.
Ogni decisione deve ridurre attrito non necessario:
- meno tap;
- meno schermate;
- meno campi;
- meno decisioni;
- default chiari;
- progressive disclosure;
- recovery evidente;
- permessi just-in-time;
- forte gerarchia visiva.

POSSIBILE != NECESSARIO.
Non aggiungere feature, backend, AI, sync, schermate o framework solo perché
tecnicamente possibili.

======================================================================
7. GOLDEN COMPONENT LIBRARY — COPY FIRST
======================================================================

Ordine di preferenza:

1. CERTIFIED GOLDEN interno.
2. COPY-READY GOLDEN interno.
3. CERTIFIED DONOR interno.
4. DRAFT/CANDIDATE Golden con audit per-app.
5. donor interno già usato.
6. OSS con licenza compatibile.
7. nuova implementazione.

EXTEND BEFORE DUPLICATE.
COPY FIRST, ANALYZE THE DELTA.

Stati:
- CERTIFIED DONOR;
- COPY-READY GOLDEN;
- CERTIFIED GOLDEN;
- CANDIDATE;
- DRAFT / PROCESS CANDIDATE;
- COPY-READY PROCESS;
- DEPRECATED.

Un Golden generalizzato NON è CERTIFIED solo perché il donor originale funziona.

8. GOLDEN FRESHNESS / STALENESS
======================================================================

Ogni Golden provider/platform-sensitive deve progressivamente registrare:

```text
lastReviewedAt:
providerSensitive: yes | no
testedPackageVersion:
testedPlatformVersion:
freshnessStatus: CURRENT | NEEDS_REVIEW | STALE | DEPRECATED
replacement:
```

Prima di usare in produzione guidance sensibile a:
- SDK/API;
- store policy;
- billing;
- AdMob;
- OAuth;
- Android background execution;
- provider cloud;
verificare la documentazione corrente se la freschezza non è CURRENT.

Stale knowledge deve essere marcata, non fidata silenziosamente.

======================================================================
9. REUSE-FIRST / OSS RECONNAISSANCE
======================================================================

Prima di sviluppare un modulo non coperto bene dai Golden:
- cercare normalmente 3-5 progetti OSS simili quando il costo è giustificato;
- confrontare architettura, qualità, manutenzione, test e licenza;
- riusare codice solo se licenza compatibile;
- altrimenti riusare concetti/pattern e riscrivere;
- registrare provenance significativa.

Fonte Flutter Clean Architecture approvata come bacino di discovery:
https://github.com/topics/flutter-clean-architecture-example

Applicare:
GOLDEN_OSS_REUSE_RECONNAISSANCE_FLUTTER_v1_DRAFT.txt
GOLDEN_PROVENANCE_REUSE_LEDGER_v1_DRAFT.txt

======================================================================
10. ARCHITETTURA STANDARD
======================================================================

Usare la minima architettura che supporta in sicurezza il prodotto.
Preferire confini chiari:

Presentation
-> Domain / Use Cases quando utili
-> Repository / Data
-> Provider / Platform / Infrastructure

Regole:
- business logic fuori dai widget;
- provider DTO fuori dal domain;
- dipendenze verso l'interno;
- repository testabili;
- provider sostituibili;
- evitare service locator globale indiscriminato;
- evitare singleton quando nascondono ownership/lifecycle;
- evitare file monolitici solo quando creano rischio reale/costo di modifica;
- non refactorizzare per estetica architetturale.

======================================================================
11. DEPENDENCY ADMISSION RULE
======================================================================

Ogni nuova dipendenza deve giustificare almeno:
- valore prodotto;
- footprint/app size;
- RAM/CPU/batteria;
- permessi;
- privacy/telemetria;
- background behavior;
- compatibilità Web/iOS/Android;
- manutenzione e release cadence;
- licenza;
- possibilità di rimozione/adapter.

Non aggiungere package per poche righe di logica stabile facilmente mantenibile.
Non sacrificare però capacità reale per pochi MB quando la dipendenza porta
valore significativo.

======================================================================
12. LOCAL-FIRST / OFFLINE TRUST
======================================================================

Per default le utility devono restare utili senza rete quando il dominio lo
consente.

Verificare:
- source of truth;
- comportamento offline;
- pending writes;
- retry;
- conflitti;
- cache vs dati canonici;
- sync opzionale;
- export;
- recovery.

Login, billing e cloud non devono bloccare valore locale salvo requisito di
prodotto esplicito.

OFFLINE CLAIM != OFFLINE REALITY.
Non mostrare contenuto come "scaricato/offline" se i file/pack reali non sono
presenti e verificati.

======================================================================
13. PRODUCT TRUTH / DIAGNOSTIC TRUTH
======================================================================

PRODUCT TRUTH:
La UI non deve dichiarare:
- downloaded;
- protected;
- connected;
- synced;
- backed up;
- healthy;
- premium;
- delivered;
se lo stato reale non lo dimostra.

DIAGNOSTIC TRUTH:
"chiamata API riuscita" o "nessuna eccezione" NON equivalgono a capability
verificata.

Esempi:
- permission granted != service healthy;
- notification scheduled != notification delivered;
- file path registrato != file leggibile;
- billing callback != entitlement valido;
- download completed flag != checksum verified;
- FGS start requested != monitor operativo.

======================================================================
14. DATA DISCIPLINE & INTEGRITY
======================================================================

Ogni write deve preservare stato valido.
Verificare:
- identity;
- schema version;
- migration;
- atomicità;
- crash consistency;
- idempotenza;
- referential integrity;
- dedup;
- timestamps/revision;
- lifecycle;
- retention;
- cleanup;
- media references.

Per Data Safety applicare quando pertinenti:
- GOLDEN_BACKUP_RECOVERY_FLUTTER_v1_DRAFT.txt
- GOLDEN_ENTITY_LIFECYCLE_TRASH_FLUTTER_v1_DRAFT.txt
- GOLDEN_MEDIA_ASSET_STORE_FLUTTER_v1_DRAFT.txt

Restore/import critici:
STAGE -> VALIDATE -> SAFETY SNAPSHOT -> COMMIT -> RECONCILE -> CLEANUP.

======================================================================
15. BACKUP / RECOVERY
======================================================================

Backup user-owned data deve essere:
- versionato;
- inspectable;
- bounded;
- integrity checked;
- media/reference aware;
- rollback-safe;
- compatibile con migrazioni previste.

BACKUP CREATED != RESTORE VERIFIED.
Per file/media reali, la certificazione richiede failure-path e physical
validation quando pertinente.

======================================================================
16. LIFECYCLE / DELETE / TRASH
======================================================================

Default contenuti:
ACTIVE -> TRASHED -> RESTORE oppure PURGE.
ARCHIVE != TRASH.

Purge deve considerare:
- figli;
- media;
- reminder;
- sync;
- reference;
- derived index;
- collaborative ownership.

Soft delete non deve distruggere ciò che serve al restore.

======================================================================
17. MEDIA / FILE
======================================================================

Preferire storage privato, import tramite copia controllata e ID content-addressed
quando utile.

Original != thumbnail != derivative != cache.
GC deve essere reference-aware.
Gli oggetti nel Trash contano come reference finché non vengono purgati.

Private file URI non devono essere trasferiti cross-app come contratto portabile.

======================================================================
18. IMPORT / EXPORT / PORTABILITY
======================================================================

Applicare:
GOLDEN_IMPORT_EXPORT_PORTABILITY_FLUTTER_v1_DRAFT.txt

Pipeline preferita:
SOURCE -> ADAPTER -> STAGING MODEL -> VALIDATION -> REVIEW/PREVIEW quando utile
-> ATOMIC COMMIT -> IMPORT REPORT.

Regole:
- external ID != canonical local ID;
- conservare provenance/fingerprint quando utile;
- re-import deve essere idempotente o esplicitamente conflittuale;
- import != continuous sync;
- reference resolution deterministica;
- lossiness deve essere dichiarata;
- export deve privilegiare formati portabili e verificabili.

Applicare:
GOLDEN_ECOSYSTEM_BRIDGE_FLUTTER_v1_DRAFT.txt

28. SECURE STORAGE / PRIVACY
======================================================================

Minimizzare dati e permessi.
Secret/token/password non devono entrare in repository, log, backup portabile o
analytics.

Per dati sensibili:
- encryption at rest quando giustificata;
- Keystore/Keychain tramite adapter;
- fail closed;
- backup/Auto Backup policy esplicita;
- export/import policy esplicita;
- biometria come gate UX solo se semanticamente corretta.

CORS != authentication.

- test;

Fastlane:
- build-once preferito;

35. RELEASE REALITY / EVIDENCE LADDER
======================================================================

Applicare:
GOLDEN_RELEASE_REALITY_PHYSICAL_VALIDATION_v1_DRAFT.txt

Evidence Ladder:

IMPLEMENTED
-> STATICALLY CHECKED
-> TESTED
-> CI GREEN
-> ARTIFACT BUILT
-> TRUSTED RUNTIME VERIFIED
-> PHYSICAL DEVICE VERIFIED
-> DISTRIBUTION VERIFIED
-> STORE READY
-> PRODUCTION RELEASED

Ogni affermazione deve fermarsi al livello realmente provato.

DEBUG BUILD != RELEASE APK != AAB != GITHUB ARTIFACT != PLAY INTERNAL
!= STORE READY != PRODUCTION RELEASE.

SAME-ARTIFACT RULE:
build once -> identify exact bytes -> verify exact bytes -> distribute exact bytes
quando possibile.

======================================================================
36. PHYSICAL VALIDATION
======================================================================

Obbligatoria prima di CERTIFIED per capability materialmente dipendenti da:
- sensori;
- camera/scanner;
- biometria/Keystore;
- GPS/background;
- FGS;
- OEM battery behavior;
- OAuth/deep link release callback;
- notification delivery;
- file picker/provider;
- physical restore;
- Play model/asset delivery;
- billing/store purchase;
- cross-app deep link/transport.

PASS / FAIL / BLOCKED / NOT VERIFIED devono restare distinti.

======================================================================
37. PERFORMANCE / BATTERY / APP SIZE
======================================================================

Performance, batteria e peso sono requisiti di prodotto.
Verificare:
- startup;
- jank/frame;
- main-thread work;
- RAM;
- bitmap/media;
- I/O;
- polling;
- duplicate listener;
- background wakeups;
- APK/AAB size;
- download/model pack size;
- dependency bloat.

Preferire app leggere, ma non sacrificare una capability utile solo per pochi MB.

======================================================================
38. WEB PREVIEW / TARGET BOUNDARY
======================================================================

Per Flutter Web fornire preview stabile quando tecnicamente sensato.

Web Preview può verificare:
- UI;
- navigation;
- localization;
- responsive;
- pure/shared logic.

Non certifica automaticamente:
- Android service;
- sensor;
- native storage;
- real push;
- billing;
- Play delivery;
- biometric;
- background restrictions.

Native-only feature su Web:
- adapter/stub/mock chiaramente identificato;
- mai finta equivalenza funzionale.

======================================================================
39. AUDIT — TRIGGER E METODO
======================================================================

Quando l'utente chiede audit / audit profondo / gap analysis / come siamo messi:

1. fissare una baseline reale;
2. verificare Product Bible/roadmap;
3. verificare architettura;
4. verificare data/lifecycle/storage;
5. verificare native services/permissions/capabilities;
6. verificare UI/UX/accessibility/localization;
7. verificare Premium/monetization;
8. verificare tests/CI;
9. verificare performance/battery/size;
10. verificare release/deploy/evidence.

Classificare:
- FATTO VERIFICATO;
- INFERENZA RAGIONEVOLE;
- NON VERIFICATO;
- GAP REALE;
- NON NECESSARIO ORA;
- IMPLEMENTATO DIVERSAMENTE MA ADEGUATO.

Per ogni gap reale:
- impatto;
- rischio;
- priorità;
- dipendenze;
- correzione minima sicura.

Chiedersi sempre:
COSA NON STANNO VERIFICANDO I GATE VERDI?

======================================================================
40. AUDIT != IMPLEMENTAZIONE
======================================================================

Salvo richiesta esplicita, durante un audit:
- non modificare codice;
- non fare refactor;
- non aggiungere feature;
- non cambiare Premium;
- non fare merge;
- non pubblicare release.

Se l'utente chiede AUDIT + RISOLVI:
- correggere prima P0/P1;
- poi P2 ad alto valore/costo;
- aggiungere regression test;
- aggiornare documentazione pertinente;
- rieseguire i gate reali disponibili.

======================================================================
41. AUDIT + ROADMAP
======================================================================

Prima audit, poi roadmap.
Non assumere che la roadmap esistente sia corretta.

La nuova roadmap deve:
- seguire dipendenze tecniche reali;
- proteggere data safety e architecture;
- inserire foundation/hardening prima della feature se necessario;
- accorpare step compatibili;
- non moltiplicare micro-step inutilmente;
- mantenere main stabile;
- avere Definition of Done verificabile.

======================================================================
42. BUG / SEVERITY
======================================================================

P0:
- perdita/corruzione dati;
- app non avviabile;
- compromissione security critica;
- release unsafe grave;
- monetizzazione core completamente rotta se blocca il prodotto.

P1:
- core feature non funziona;
- capability dichiarata ma falsa;
- governance/security bypass serio;
- restore/sync/permission failure importante;
- UI che impedisce il core flow.

P2:
- bug secondario;
- UX significativa ma non bloccante;
- performance localizzata;
- visual issue importante.

P3:
- polish;
- microcopy;
- microanimazioni;
- refactor non urgente.

Non classificare ogni mancanza come P0.

======================================================================
43. QA / TEST DISCIPLINE
======================================================================

Distinguere:
- unit;
- integration;
- migration;
- failure-path;
- widget/UI;
- instrumentation/device;
- E2E/Maestro;
- visual regression;
- physical acceptance.

Self-test nell'implementazione è utile ma non sostituisce una oracle indipendente.

Ogni bug fix importante deve avere test anti-regressione quando tecnicamente
ragionevole.
