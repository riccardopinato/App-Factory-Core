GOLDEN COMPONENTS — CROSS-APP REUSE AUDIT
Versione 1.0 — 01/10/2026
Tipo audit: cross-project reuse / redundancy audit
Master Prompt di riferimento: v19 SLIM
Golden Index di riferimento: v2

======================================================================
0. SCOPO
======================================================================

Obiettivo:
individuare infrastruttura ripetuta tra le app del Project e selezionare ciò che
conviene trasformare in Golden Component copy-ready, evitando sia duplicazione
sia standardizzazioni premature.

Questo NON è un release audit completo di ogni singola app.
È un audit trasversale orientato a:
- REUSE-FIRST;
- COPY-FIRST;
- riduzione errori;
- riduzione contesto/token;
- bootstrap più rapido delle nuove app;
- standardizzazione solo dove esiste evidenza reale.

Baseline esaminate:
- Anna's Diary;
- Notes-Ecosistema;
- CamperBoss;
- TrailPath;
- FrameLab;
- Notification-Control;
- Battery Guard;
- AppLab;
- Send-to-PC come riferimento secondario;
- Backlog idee app del Project.

2. RIDONDANZE FORTI — DA TRASFORMARE IN GOLDEN
======================================================================

----------------------------------------------------------------------
A. GOLDEN_BACKUP_RECOVERY_FLUTTER_v1
Priorità: P0
Stato candidato: READY FOR EXTRACTION
----------------------------------------------------------------------

Evidenza verificata:
- Anna's Diary:
  ZIP versionato, manifest, data.json, media separati, SHA-256, limiti dimensione,
  validazione, backward compatibility, restore safety.
- Notes-Ecosistema:
  BackupSnapshot, MediaBundle, limiti anti-zip-bomb, validazione asset,
  disaster recovery, export portabile.
- CamperBoss:
  BackupService astratto, BackupManifest, SHA-256, inspection,
  restore replace/merge, backup automatico pre-restore.
- Notification-Control:
  BackupRepository + EncryptedBackupCodec lato Android nativo.

Standard da estrarre:
- BackupManifest;
- schemaVersion;
- appVersion;
- exportedAt;
- file manifest + SHA-256;
- limiti compressi/espansi/singolo file;
- inspect-before-restore;
- restore atomico o rollback-safe;
- strategia replace / merge;
- automatic safety snapshot prima del restore;
- adapter app-specifico per serializzare il dominio;
- media/file separati dal JSON principale;
- backward compatibility dichiarata.

Donor principale consigliato:
Anna's Diary + CamperBoss.

Perché:
Anna ha hardening media/integrità molto maturo;
CamperBoss ha un contratto BackupService più generalizzabile.

3. CANDIDATI IMPORTANTI — NON STANDARDIZZARE ANCORA COME CODICE UNICO
======================================================================

----------------------------------------------------------------------
I. LOCAL-FIRST DATABASE / REPOSITORY
Stato: DEFER — SERVONO VARIANTI
----------------------------------------------------------------------

Evidenza:
- Anna: Sembast + deltas;
- FrameLab: Drift;
- TrailPath: Drift;
- CamperBoss: sqflite / repository locali;
- Notification-Control: Room.

Conclusione:
non esiste un unico backend corretto per tutte le app.

Standardizzare invece:
- repository interfaces;
- migration contract;
- transaction/atomicity contract;
- schema versioning;
- corruption behavior;
- test contract.

In futuro creare varianti:
- GOLDEN_DRIFT_LOCAL_DB_FLUTTER;
- GOLDEN_SEMBAST_LOCAL_STORE_FLUTTER;
- eventuale GOLDEN_SQLITE_REPOSITORY_FLUTTER.

----------------------------------------------------------------------
J. SEARCH / FTS / RETRIEVAL
Stato: DEFER — TROPPO DOMAIN-SPECIFIC
----------------------------------------------------------------------

Evidenza:
- Notes: lexical + semantic + RRF;
- Anna: deterministic global search + derived connections;
- CamperBoss: local search service;
- Notification-Control: Room FTS.

Conclusione:
standardizzare ora solo:
- SearchQuery contract;
- debounce;
- incremental UI;
- filter model;
- empty/error state;
- ranking tests.

NON imporre un unico motore.

----------------------------------------------------------------------
K. OFFLINE SYNC / OUTBOX / CONFLICTS
Stato: DEFER — ALTA UTILITÀ MA PROVIDER-SPECIFIC
----------------------------------------------------------------------

Evidenza:
- Anna: Supabase incremental sync, tombstones, cursors, queues;
- Notes: GitHub/shared live sync e background;
- altri progetti: local-only.

Possibile futuro Golden:
- mutation envelope;
- pending queue;
- retry policy;
- tombstone;
- idempotency;
- conflict result;
- sync cursor;
- health state.

Ma provider/backend adapter devono restare separati.

----------------------------------------------------------------------
L. BACKGROUND / FOREGROUND SERVICE
Stato: DEFER — CREARE GOLDEN ANDROID SPECIFICO PIÙ AVANTI
----------------------------------------------------------------------

Evidenza:
- Battery Guard;
- TrailPath;
- Notification-Control;
- Pocket Guard/Tabletop nel Project.

È molto riusabile ma dipende da:
- FGS type;
- permission;
- sensor/location use case;
- boot receiver;
- OEM restrictions;
- battery policy;
- Play policy.

Serve audit dedicato prima di congelare una base comune.

----------------------------------------------------------------------
M. MAP / ROUTING
Stato: KEEP SPECIALIZED
----------------------------------------------------------------------

TrailPath e CamperBoss hanno overlap, ma:
- outdoor routing;
- camper dimensions/restrictions;
- offline map scope;
- navigation behavior
sono semanticamente diversi.

Condividere primitive/adapters solo quando davvero compatibili.
Non creare un “mega routing Golden” prematuro.

6. IMPATTO SULLE NUOVE APP
======================================================================

Con gli attuali 7 Golden + gli 8 candidati sopra,
una nuova utility potrebbe partire con quasi tutta l'infrastruttura comune già
definita:

- auth;
- profilo;
- localizzazione;
- theme;
- secure storage;
- notifications;
- CI/release/deploy;
- onboarding;
- permissions/capability health;
- backup/recovery;
- lifecycle/trash;
- media;
- premium contract;
- UI shell/states;
- QA/certification.

Resterebbero principalmente:
- dominio specifico;
- data model specifico;
- feature distintiva;
- eventuali native API specialistiche;
- monetizzazione provider-specific;
- sync provider-specific.

Questo è il punto in cui la creazione delle nuove app diventa realmente
“assembly-first” invece di “reinvent-first”.

======================================================================
7. EFFETTO SU CONTESTO / MEMORIA
======================================================================

Nuova regola operativa consigliata:

Per una nuova app NON leggere interamente i donor project se esiste già un
Golden Component certificato.

Leggere:
1. Master Prompt;
2. Golden Index;
3. solo i Golden richiesti dalla nuova app;
4. donor originale soltanto se:
   - il Golden non copre il caso;
   - serve verificare una regressione;
   - si sta creando la versione successiva del Golden.

Questo riduce:
- contesto;
- token;
- riletture GitHub;
- contraddizioni tra versioni;
- dipendenza dalla memoria delle vecchie chat.

======================================================================
8. VERDETTO
======================================================================

PASS — GOLDEN LIBRARY DA ESPANDERE.

8 nuovi moduli selezionati:
- 6 pronti per estrazione completa;
- 1 pronto come entitlement contract ma non come billing provider;
- 1 pronto come UI shell/states.

Da NON standardizzare ancora:
- unico database;
- unico search engine;
- unico sync provider;
- unico background engine;
- mega routing layer.

Principio:
standardizzare ciò che è realmente uguale;
astrarre ciò che varia per provider;
lasciare specifico ciò che appartiene al dominio dell'app.
