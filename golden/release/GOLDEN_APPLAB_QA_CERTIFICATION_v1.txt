======================================================================
1. SCOPO
======================================================================

Standardizzare il lato CLIENT di integrazione delle nostre app con AppLab.

NON duplicare AppLab dentro ogni repo.

======================================================================
2. TRUST BOUNDARY
======================================================================

Il target sotto test non deve poter dichiarare da solo che la propria evidence
è trusted.

Evidence trusted deve legare almeno:
- target repository;
- immutable SHA/ref risolto;
- package/application ID;
- workflow/run;
- artifact SHA-256;
- verifier/AppLab identity/version quando disponibile.

======================================================================
3. LIVELLI
======================================================================

FAST
- controlli rapidi mirati;
- non equivale a certification.

FULL
- analyze/test/build + runtime/evidence ampia per lo scope.

CERTIFIED
- evidence trusted;
- artifact identity;
- acceptance criteria;
- native physical validation separata quando richiesta.

======================================================================
4. CLIENT INTEGRATION CONTRACT
======================================================================

Ogni app candidata deve fornire/configurare almeno:

```text
repository:
immutableTargetRef:
packageId:
projectType:
flutterVersion/toolchain:
releaseArtifactPattern:
primaryJourney:
physicalValidationRequired:
physicalCapabilities:
```

Baseline reusable workflow validata nel pilot 14/10/2026:

```yaml
permissions:
  contents: read
  actions: read

jobs:
  applab:
    uses: riccardopinato/AppLab/.github/workflows/external-project-runner.yml@<IMMUTABLE_APPLAB_SHA>
    with:
      repository: <owner/repo>
      ref: ${{ github.event.pull_request.head.sha || github.sha }}
      source_ref: ${{ github.head_ref || github.ref_name }}
      working_directory: "."
      flutter_version: <validated-flutter-version>
      java_version: "<validated-java-version>"
      package_id: <android.package.id>
      apk_path: <release-apk-path>
      build_command: <per-app-release-build-command>
      analysis_mode: full
      run_maestro: true
      maestro_flow: <primary-flow>
      history_key: <stable-project-history-key>
      config_fingerprint: <stable-client-contract-version>
      cache_verification: false
      publish_release_artifact: false
```

Regole:
- pin AppLab a SHA immutabile già validato; non usare branch/tag mobile;
- il normale gate PR può usare FULL per trusted runtime verification;
- usare CERTIFICATION solo quando il progetto intende valutare anche i gate di
  release/certification previsti;
- mantenere build command, toolchain e artifact path per-app espliciti;
- se il progetto richiede `prepare_command` / `post_pub_get_command` per
  materializzare scaffold o asset generati, configurarli nel caller e copiare
  solo valori già validati nel progetto reale;
- il target non può dichiarare da solo PASS/CERTIFIED.

Quando esistono requisiti real-device, aggiungere `applab.project.json`
(schema v1) con `physical_validation.required=true` e capability supportate,
per esempio:

```json
{
  "schema_version": 1,
  "project_type": "flutter",
  "working_directory": ".",
  "package_id": "com.example.app",
  "toolchain": {
    "flutter_version": "3.x.y",
    "java_version": "17"
  },
  "release_artifact_pattern": "build/app/outputs/flutter-apk/app-release.apk",
  "journeys": {
    "primary": ".maestro/applab-smoke.yaml"
  },
  "physical_validation": {
    "required": true,
    "capabilities": ["biometrics", "keystore", "notifications"]
  }
}
```

Questa metadata è intent non trusted: può rendere la certification più severa,
mai ridurre un requisito fisico già esistente.

======================================================================
5. EVIDENCE MINIMA
======================================================================

Quando disponibile:
- resolved SHA;
- build log;
- APK/AAB hash;
- install/launch result;
- Maestro journey result;
- screenshots;
- UI hierarchy;
- Logcat;
- crash/ANR scan;
- visual regression result;
- evidence manifest.

======================================================================
6. NON CONFONDERE
======================================================================

AppLab runtime PASS != Play Internal Testing PASS.
AppLab emulator PASS != physical sensor/device PASS.
Visual regression PASS != product UX approval.
Artifact built != same artifact distributed.

======================================================================
7. FAILURE SEMANTICS
======================================================================

PASS
- evidence prevista presente e conforme.

FAIL
- evidence mostra regressione/violazione.

BLOCKED
- dipendenza/tool/device/evidence impedisce la verifica.

NOT VERIFIED
- scope non eseguito.

======================================================================
8. REUSE RULE
======================================================================

Per nuove app:
- usare questo adapter;
- non copiare interamente AppLab;
- non inventare un secondo evidence manifest;
- non rendere target-authored test l'unica authority trusted.
