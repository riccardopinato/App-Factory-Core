======================================================================
1. SCOPO
======================================================================

Definire un contratto operativo repository-local, tool-neutral e versionato per
gli agenti di coding senza creare una seconda Product Bible o un secondo Master
Prompt.

Il file canonico è AGENTS.md.

AGENTS.md governa COME l'agente lavora nel repository.
NON sostituisce:
- Product Bible;
- Roadmap;
- CURRENT.yaml;
- Master Prompt;
- Golden Rules;
- documentazione tecnica specifica;
- implementazione e test reali.

======================================================================
2. SOURCE OF TRUTH / PRECEDENZA
======================================================================

Per App-Factory-Core:

CURRENT.yaml
-> Master Prompt
-> Golden Index / Registry
-> Golden pertinenti
-> AGENTS.md come contratto operativo dell'agente
-> moduli governance/agents pertinenti
-> implementazione reale

Per una singola app, Product Bible e Roadmap restano rispettivamente verità di
prodotto ed esecuzione.

Un bridge tool-specific NON deve diventare una policy concorrente.

======================================================================
3. STRUTTURA CANONICA
======================================================================

Baseline v1:

AGENTS.md

governance/agents/
- code-hygiene.md
- testing-validation.md
- git-workflow.md
- research-reuse.md

AGENTS.md deve restare un entrypoint compatto.
Caricare solo i moduli pertinenti al task/phase corrente.

PORTABILITY BUDGET iniziale:
- target <= 200 righe;
- target <= 24.000 byte UTF-8.

Il budget è una guardrail della Factory, non una proprietà universale dello
standard AGENTS.md.

======================================================================
4. TOOL-SPECIFIC BRIDGES
======================================================================

Se un tool richiede:
- CLAUDE.md;
- .github/copilot-instructions.md;
- Cursor rules;
- GEMINI.md;
- altro adapter;

preferire:
- pointer/import sottile quando supportato;
oppure
- generazione deterministica dalla source canonica.

NON mantenere manualmente più copie indipendenti della stessa policy.

Quando esiste almeno un bridge duplicativo/generato:
SOURCE AGENTS.md
-> deterministic adapter
-> drift check
-> CI fail se target generato diverge.

Se nessun bridge tool-specific esiste, il drift gate è N/A e NON blocca
l'adozione del contratto canonico.

L'automazione multi-tool completa resta evoluzione successiva: non va introdotta
finché un tool reale non la richiede.

======================================================================
5. PROTECTED GOVERNANCE
======================================================================

Le istruzioni centrali non devono auto-modificarsi perché un agente riceve una
correzione durante una sessione.

Una modifica a:
- AGENTS.md;
- moduli governance/agents;
- Master;
- Golden;
- resolver/validator;

segue il normale flusso App Factory:
baseline -> branch -> change -> validation -> PR -> review -> merge.

Questo evita self-modifying policy non revisionata.

======================================================================
6. DOWNSTREAM APP CONTRACT
======================================================================

Per nuove app, il bootstrap deve prevedere un AGENTS.md repository-local.

Il contratto app-level può aggiungere:
- stack/command reali;
- protected paths;
- capability native critiche;
- build/test command;
- project-specific seams;
- validation specifica.

Non può contraddire Product Bible, Roadmap, Master o Golden applicabili.

Per app esistenti:
- nessun mass update automatico;
- adottare al prossimo bootstrap/modernization/audit sostanziale quando utile;
- preservare eventuali istruzioni locali valide tramite merge/delta esplicito.

======================================================================
7. INSTRUCTION VALIDATION
======================================================================

Le istruzioni sono software operativo per agenti e possono fallire.

Quando una regola contiene behavior deterministico:
- validarla con script/schema/check quando pratico.

Quando una regola ad alto rischio dipende dalla comprensione del modello:
- considerare eval isolata;
- positive control;
- negative control;
- regression case basato su failure reale.

KEYWORD PRESENT != INSTRUCTION EFFECTIVE.
