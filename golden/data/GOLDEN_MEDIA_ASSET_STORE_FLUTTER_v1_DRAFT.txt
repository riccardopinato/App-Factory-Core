======================================================================
1. SCOPO
======================================================================

Storage standard candidato per foto, audio, scansioni, documenti e allegati.

Obiettivi:
- private-by-default;
- import sicuro;
- deduplica;
- integrità;
- bounded cache;
- reference-aware cleanup;
- separazione original/thumbnail/derivative;
- adapter Web/native.

======================================================================
2. PRINCIPI
======================================================================

- non usare il path esterno dell'utente come source of truth;
- import = copia nello storage privato;
- originali immutabili per default;
- thumbnail/derivative separati;
- SHA-256 content addressing come default candidato;
- verify-on-read per asset content-addressed;
- bounded RAM cache;
- bounded derived/remote disk cache;
- Trash references contano come reference;
- GC solo per asset realmente orfani;
- backup include soltanto user-owned assets realmente referenziati.

======================================================================
3. ASSET ID
======================================================================

Original:

```text
sha256_<hex>
```

Named/derived:

```text
<namespace>_<sha256(key)>
```

Esempi:
- sha256_...
- thumb_...
- remote_...

7. CONTENT ADDRESSING
======================================================================

Candidate:

```dart
String contentAssetId(List<int> bytes) {
  final digest = sha256.convert(bytes);
  return 'sha256_$digest';
}
```

Benefici:
- deduplica naturale;
- integrity check;
- backup manifest semplice;
- original immutabile;
- meno copie duplicate.

======================================================================
8. READ INTEGRITY
======================================================================

Se assetId è `sha256_*`:

```text
read bytes
-> SHA-256
-> compare con assetId
-> mismatch:
   mark corrupt
   return typed failure/null
```

Mai servire silenziosamente un asset corrotto.

======================================================================
11. ORIGINAL / THUMBNAIL / DERIVATIVE
======================================================================

ORIGINAL
- user-owned;
- backup eligible;
- non ricostruibile se perso.

THUMBNAIL
- derived;
- ricostruibile;
- normalmente escluso dal backup.

DERIVATIVE
- se ricostruibile: escluso;
- se rappresenta un editing user-owned unico: trattarlo come original/version.

======================================================================
13. GARBAGE COLLECTION
======================================================================

Formula:

```text
stored asset ids
MINUS referenced asset ids
MINUS protected temporary/staging ids
=
candidate orphan ids
```

GC:
- debounce;
- non startup-critical;
- non durante backup/restore commit;
- no delete se asset shared da più entity.

======================================================================
14. SAFE PATH RULES
======================================================================

- bounded;
- allowlist chars;
- nessun slash;
- nessun `..`;
- nessun absolute path.

Filesystem filename:
- costruito internamente;
- mai direttamente da user input.

======================================================================
16. BRIDGE LIFECYCLE
======================================================================

Soft delete:
- NON eliminare media.

Restore:
- media deve ancora esistere.

Purge:
- rimuovere la reference;
- eseguire GC;
- eliminare solo se nessun'altra reference esiste.

======================================================================
17. BRIDGE BACKUP
======================================================================

Backup:

```text
snapshot
-> referencedAssetIds
-> read original assets
-> verify integrity
-> bundle
```

Restore:

```text
verify hashes
-> stage media
-> commit domain
-> commit staged media
-> rollback staging on failure
```

21. STAGING / TRANSACTION HARDENING — v0.2
======================================================================

Il Media Store deve supportare una fase temporanea per restore/import critici.

Contratto candidato:

```dart
abstract interface class MediaStagingSession {
  String get transactionId;
  Future<void> stage(String assetId, List<int> bytes);
  Future<void> verify();
  Future<void> commit();
  Future<void> rollback();
}
```

Regole:
- staging namespace separato dagli asset canonical;
- asset staged non visibili come canonical prima del commit;
- hash verificato dopo la scrittura fisica;
- commit idempotente;
- rollback idempotente;
- GC non tocca staging attivo;
- startup cleanup rimuove staging abbandonato solo dopo aver consultato eventuale
  recovery marker del Backup engine.

Test aggiunti:
[ ] failure durante write fisico
[ ] failure dopo write ma prima verify
[ ] failure dopo verify ma prima commit
[ ] rollback ripetuto
[ ] commit ripetuto
[ ] GC non elimina staging attivo
[ ] startup cleanup staging abbandonato
[ ] reference presente ma file canonical assente -> health error
[ ] file canonical presente senza reference -> candidato GC, non delete immediato
