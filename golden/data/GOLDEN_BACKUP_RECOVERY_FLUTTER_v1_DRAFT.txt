1. SCOPO
======================================================================

Congelare il contratto candidato di un motore Backup/Recovery comune senza
legarlo al dominio specifico dell'app.

NON è ancora un componente da copiare in produzione senza audit dedicato.

======================================================================
2. PRINCIPI
======================================================================

- backup versionato;
- manifest esplicito;
- schemaVersion + appVersion + createdAt;
- data strutturati separati dai media;
- SHA-256 per data e file;
- limiti anti zip-bomb / expansion / entry count / single-file size;
- inspect-before-restore;
- restore staged;
- safety snapshot prima del replace;
- commit atomico o rollback-safe;
- media mancanti/corrotti = errore, non backup apparentemente valido;
- dati derivati ricostruibili esclusi di default;
- secret/token/sessioni provider esclusi.

Restore standard:

READ
-> DECODE
-> VALIDATE
-> INSPECT
-> STAGE
-> SAFETY SNAPSHOT
-> COMMIT
-> RECONCILE
-> CLEANUP

4. CONTRATTO CANDIDATO
======================================================================

```dart
enum RestoreStrategy {
  replaceAll,
  merge,
}

class BackupInspection {
  const BackupInspection({
    required this.valid,
    required this.recordCounts,
    required this.mediaCount,
    required this.totalBytes,
    required this.errors,
    required this.warnings,
  });

  final bool valid;
  final Map<String, int> recordCounts;
  final int mediaCount;
  final int totalBytes;
  final List<String> errors;
  final List<String> warnings;
}

class RestoreResult {
  const RestoreResult({
    required this.strategy,
    required this.restoredRecords,
    required this.skippedRecords,
    required this.conflicts,
    required this.safetySnapshotCreated,
  });

  final RestoreStrategy strategy;
  final int restoredRecords;
  final int skippedRecords;
  final int conflicts;
  final bool safetySnapshotCreated;
}

abstract interface class BackupDomainAdapter<TSnapshot> {
  String get backupFormat;
  int get schemaVersion;

  Future<TSnapshot> captureSnapshot();
  Map<String, Object?> encodeData(TSnapshot snapshot);
  TSnapshot decodeData(Map<String, Object?> data);

  Future<Map<String, List<int>>> collectMedia(
    TSnapshot snapshot,
  );

  Future<void> validateSnapshot(TSnapshot snapshot);

  Future<void> commitRestore(
    TSnapshot snapshot, {
    required RestoreStrategy strategy,
  });

  Future<void> reconcileAfterRestore();
}

abstract interface class BackupRecoveryService {
  Future<List<int>> createBackup();

  Future<BackupInspection> inspectBackup(
    List<int> bytes,
  );

  Future<RestoreResult> restoreBackup(
    List<int> bytes, {
    RestoreStrategy strategy = RestoreStrategy.replaceAll,
  });
}
```

======================================================================
5. CREATE BACKUP
======================================================================

capture snapshot
-> validate snapshot
-> collect referenced media
-> verify media
-> encode data.json
-> hash data.json
-> hash media
-> create manifest
-> build bounded archive
-> final size check

Se un original media necessario manca:
FAIL.

======================================================================
6. RESTORE
======================================================================

- compressed-size guard;
- decode bounded archive;
- reject duplicate/unknown/unsafe paths;
- parse manifest;
- verify format/version;
- verify data hash;
- verify media size/hash;
- decode snapshot;
- validate references;
- safety snapshot;
- stage imported media;
- commit domain;
- commit staged media;
- reconcile derived indexes/reminders/sync;
- rollback staging on failure.

======================================================================
7. PATH SAFETY
======================================================================

Rifiutare:
- ../
- path assoluti
- duplicate entry
- file non dichiarati
- asset ID invalidi
- entry sopra limite
- manifest incoerente

Allowlist:
- manifest.json
- data.json
- media/<assetId>.bin
- sidecar esplicitamente registrati

14. PHYSICAL FILE ROLLBACK HARDENING — v0.2
======================================================================

Commit contract candidato:

1. creare transactionId;
2. validare manifest/data/media;
3. copiare media in staging fisico isolato;
4. verificare hash dei file realmente scritti;
5. validare tutte le reference obbligatorie contro staging + asset esistenti;
6. creare safety snapshot;
7. eseguire commit dominio;
8. promuovere staging media a canonical;
9. reconciliation;
10. eliminare marker/staging.

Failure contract:
- errore durante copia file -> dominio invariato + staging cleanup;
- errore commit dominio -> staging rollback;
- errore promozione media dopo commit -> recovery marker obbligatorio e
  riparazione deterministica, mai stato apparentemente completo con file mancanti;
- crash mid-restore -> startup recovery deve sapere se rollback o resume.
