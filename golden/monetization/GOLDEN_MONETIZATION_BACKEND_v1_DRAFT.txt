GOLDEN MONETIZATION BACKEND
Versione: v1 DRAFT — 25/10/2026

STATO
DRAFT / PROCESS CANDIDATE — BACKEND PILOT PENDING

SCOPO

Definire il backend riutilizzabile App Factory per verificare acquisti digitali,
sincronizzare entitlement e reagire agli eventi dei provider senza rendere il
client mobile autoritativo.

Questo Golden è complementare a:
- GOLDEN_ENTITLEMENT_CONTRACT_FLUTTER_v1.txt
- GOLDEN_PLAY_BILLING_LIFETIME_ENTITLEMENT_FLUTTER_v1_DRAFT.txt
- eventuali adapter futuri App Store / RevenueCat.

Non sostituisce i contratti provider-specific.

======================================================================
1. PRINCIPIO CENTRALE
======================================================================

CLIENT CLAIM != PURCHASE VERIFIED != ENTITLEMENT ACTIVE

Il client può:
- iniziare un acquisto;
- ricevere purchase token / receipt;
- chiedere restore;
- mostrare stato locale/cache.

Il client NON è authority finale per:
- autenticità dell'acquisto;
- unicità del purchase token;
- entitlement definitivo;
- revoche/rimborsi;
- acknowledgement server-side;
- stato subscription;
- antifrode.

L'authority monetization deve essere:
1. provider store per lo stato di acquisto;
2. backend App Factory per la proiezione entitlement;
3. client come cache/consumer dell'entitlement.

======================================================================
2. QUANDO USARLO
======================================================================

USARE il backend quando esiste almeno uno di questi casi:
- one-time product / lifetime entitlement in-app;
- subscription;
- entitlement cross-device;
- restore affidabile;
- refund/revoke handling;
- RTDN / server notifications;
- più app che condividono infrastruttura monetization;
- necessità antifrode superiore al puro client-side.

NON USARLO automaticamente quando:
- l'app è semplicemente PAID UPFRONT nello store;
- non esistono entitlement in-app;
- il provider store gestisce direttamente il diritto di installazione;
- aggiungere il backend non migliora un requisito reale.

Regola App Factory:

> Monetization infrastructure is admitted only when it protects or synchronizes
> a real entitlement. Paid-upfront apps do not receive a backend by default.

======================================================================
4. CONTRATTO API MINIMO
======================================================================

Endpoint logici canonici:

POST /v1/monetization/verify
GET  /v1/monetization/entitlements
POST /v1/monetization/restore
POST /v1/providers/google/rtdn

Il naming HTTP concreto può cambiare per stack/serverless, ma i ruoli no.

VERIFY request minimo:

{
  "appId": "canonical_app_id",
  "platform": "android",
  "packageName": "com.example.app",
  "productId": "product_id",
  "purchaseToken": "<opaque>",
  "principal": {
    "type": "account|accountless",
    "id": "<opaque stable id when available>"
  }
}

VERIFY response minimo:

{
  "verification": "VERIFIED|PENDING|REJECTED|UNKNOWN",
  "entitlement": {
    "id": "pro",
    "status": "ACTIVE|INACTIVE|UNKNOWN",
    "validUntil": null,
    "source": "google_play"
  },
  "serverTime": "RFC3339",
  "revision": 1
}

Non restituire al client segreti provider o credenziali service account.

======================================================================
6. GOOGLE PLAY ADAPTER — BASELINE 25/10/2026
======================================================================

Provider baseline verificata:
- Google Play Billing Library 9.1.0;
- Google Play Developer API v3;
- one-time products model con purchase options / offers;
- RTDN per subscriptions e one-time products.

Flusso one-time non-consumable:

CLIENT PURCHASE
  ↓
purchaseToken
  ↓
POST /verify
  ↓
backend verifica token con Google Play Developer API
  ↓
state == PURCHASED ?
  ├─ no -> PENDING / REJECTED / UNKNOWN
  └─ yes
       ↓
       transazione entitlement
       ↓
       acknowledge server-side se necessario
       ↓
       ACTIVE

Mai concedere entitlement su PENDING.

Acknowledgement:
- eseguirlo immediatamente dopo la concessione affidabile dell'entitlement;
- renderlo idempotente;
- non considerare un timeout acknowledgement come prova di mancato acquisto;
- riconciliare successivamente.

======================================================================
7. OFFERS / PRICING
======================================================================

Prezzi e offerte sono provider-owned configuration.

Il client NON deve hardcodare:
- prezzo locale;
- valuta;
- percentuale sconto;
- testo "prezzo precedente";
- eligibility dell'offerta.

Il client deve visualizzare i dati restituiti dal provider/store SDK.

Per one-time products Google Play:
- supportare purchase option;
- supportare discount offer quando disponibile;
- selezionare e passare l'offer token corretto;
- fallback al prezzo pieno quando l'utente non è eligible.

Il backend può mantenere mirror/catalog metadata, ma non deve inventare
eligibility diversa dal provider.

======================================================================
8. ACCOUNT E ACCOUNTLESS
======================================================================

ACCOUNT MODE
Usare un user/principal stabile dell'app.
Quando supportato, usare identificatori offuscati provider per legare il flow
all'account senza inviare PII raw.

ACCOUNTLESS MODE
Non obbligare login solo per monetization.

Per app senza account:
- Play/App Store restano origine del restore;
- il client recupera gli acquisti del provider;
- reinvia il token al backend;
- il backend riverifica;
- l'entitlement viene ricostruito.

Non usare Android ID, advertising ID, email implicite o fingerprint hardware
come surrogato di account.

======================================================================
9. IDEMPOTENZA
======================================================================

Ogni operazione deve tollerare retry.

VERIFY:
same purchaseToken
-> same purchase ledger row
-> no duplicate entitlement

RTDN:
same messageId
-> no duplicate provider call / projection

ACKNOWLEDGE:
already acknowledged
-> success-equivalent

ENTITLEMENT:
same source purchase + revision
-> deterministic projection

======================================================================
10. RTDN / EVENT-DRIVEN RECONCILIATION
======================================================================

Il backend deve supportare provider notifications quando il prodotto le usa.

Google Play:
Pub/Sub RTDN
  ↓
dedupe messageId
  ↓
NON fidarsi del payload come stato finale
  ↓
rileggere purchase status dal Google Play Developer API
  ↓
aggiornare purchase ledger
  ↓
riprojettare entitlement
  ↓
registrare evidence

Per one-time products gestire almeno:
- PURCHASED;
- CANCELED / revoked quando notificato;
- voided purchase reconciliation quando pertinente.

Una notifica duplicata non deve generare doppie operazioni.

======================================================================
11. UNKNOWN / OFFLINE / GRACE
======================================================================

Seguire GOLDEN_ENTITLEMENT_CONTRACT_FLUTTER_v1.

NETWORK FAILURE != FREE
BACKEND FAILURE != PREMIUM
CACHE PRESENT != PURCHASE VERIFIED FOREVER

Il client può usare una cache firmata/versionata secondo il contratto prodotto.

Per lifetime:
- entitlement verificato può essere cached localmente;
- restore/reconciliation deve poter correggere refund/revoke;
- UNKNOWN deve essere rappresentato esplicitamente;
- policy offline deve essere definita per-app.

======================================================================
12. SECURITY
======================================================================

OBBLIGATORIO:
- provider service credentials solo server-side;
- secret manager / environment secrets;
- TLS;
- auth/rate limit sugli endpoint sensibili;
- purchase token non nei log applicativi;
- errori redatti;
- least privilege sul service account;
- separazione prod/test;
- audit trail;
- replay protection tramite token uniqueness;
- entitlement grant dopo verifica provider;
- nessun QA override in production.

NON USARE:
- shared secret statico dentro APK;
- client boolean "isPro" come authority;
- orderId come unica chiave;
- PII non necessaria;
- log di receipt/token raw.

======================================================================
13. FAILURE MODEL
======================================================================

Stati distinti:

PURCHASE_PROVIDER_UNAVAILABLE
BACKEND_UNAVAILABLE
PURCHASE_PENDING
PURCHASE_REJECTED
PURCHASE_VERIFIED
ACK_PENDING
ENTITLEMENT_ACTIVE
ENTITLEMENT_INACTIVE
ENTITLEMENT_UNKNOWN

Mai comprimere tutti gli errori in:
"Acquisto non riuscito".

Il client deve poter distinguere:
- riprova;
- acquisto ancora pending;
- restore;
- entitlement verificato ma ack da riconciliare;
- configurazione catalogo mancante.

16. DEPLOYMENT SHAPE
======================================================================

Il Golden non impone un vendor.

Implementazioni ammesse:
- Supabase Edge Functions + Postgres;
- Cloud Run / Functions + DB;
- Railway/Vercel server + DB;
- backend proprietario equivalente.

Requisiti invarianti:
- endpoint server-side;
- DB con uniqueness/idempotency;
- provider secrets non-client;
- atomic entitlement projection;
- health/observability;
- migration/schema versioning;
- backup/recovery adeguato al valore economico.

======================================================================
17. API / SCHEMA VERSIONING
======================================================================

Ogni response entitlement deve avere:
- schemaVersion;
- revision;
- serverTime.

Breaking change:
-> nuova API/schema version.

Non cambiare semanticamente ACTIVE/INACTIVE/UNKNOWN senza version bump.

======================================================================
19. PAID-UPFRONT BOUNDARY
======================================================================

Per un'app venduta direttamente a pagamento nello store:

STORE PAID APP
-> entitlement all'installazione gestito dal provider
-> nessun in-app product
-> nessun purchase token da verificare nel client
-> Monetization Backend = NOT REQUIRED di default

Se in futuro vengono aggiunti:
- upgrade PRO;
- subscription;
- consumable;
- cross-app entitlement;

allora rivalutare questo Golden.

======================================================================
22. REGOLE FINALI
======================================================================

1. CLIENT CLAIM != PURCHASE VERIFIED.
2. PENDING != ENTITLED.
3. purchaseToken è idempotency identity; orderId non lo sostituisce.
4. Provider notification != state finale: rileggere dal provider.
5. Entitlement projection deve essere atomica e ripetibile.
6. Secrets provider restano server-side.
7. Unknown resta unknown.
8. Paid-upfront non giustifica automaticamente un backend.
9. Prezzi/offerte non si hardcodano nel client.
10. Build green != sandbox billing verified.
