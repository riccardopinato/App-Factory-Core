1. SCOPO
Reference contract per acquisto una-tantum non consumabile che concede una
capability durevole, tipicamente Remove Ads / Lifetime.
Completa il Golden Entitlement provider-agnostic.
NON certifica Play Billing reale: manca sandbox evidence da Internal Testing.

2. BOUNDARY
UI -> Entitlement Service -> BillingAdapter -> in_app_purchase -> Store.
Product ID non sparso nei widget; store state convertito in BillingResult;
entitlement persistito separatamente dal provider SDK; Web usa stub/no-op.

3. PURCHASE STATE MACHINE
IDLE / LOADING_PRODUCT / READY / PURCHASING / PENDING / PURCHASED /
RESTORING / RESTORED / CANCELLED / FAILED / BILLING_UNAVAILABLE.

PENDING/CANCELLED/FAILED non concedono entitlement.
PURCHASED/RESTORED richiedono product ID atteso e verification boundary.

4. VERIFICATION BOUNDARY
Il donor v1 accetta per Remove Ads low-value:
- exact product ID;
- purchased/restored;
- verification payload non vuoto;
- mapping locale esplicito.

Questo significa CLIENT STORE-STATE VALIDATED.
NON significa SERVER-SIDE RECEIPT/TOKEN VERIFIED.

Per valore/fraud/subscription/account-bound entitlement maggiore, usare backend
trusted prima del durable grant.

5. DURABLE GRANT + COMPLETE PURCHASE
STORE PURCHASED/RESTORED
-> validate
-> persist durable entitlement
-> update access state
-> completePurchase quando richiesto.

Se delivery è persistita e completePurchase fallisce, non revocare
automaticamente il diritto; esporre diagnosi/retry.

6. RESTORE
Restore user-initiated, separato, idempotente, exact-product aware.
Restore call completed != entitlement restored.
