======================================================================
1. SCOPO E SOURCE OF TRUTH
======================================================================

Shared Ecosystem Core v1 è il contratto cross-app canonico dell'App Factory.

Serve per trasferimenti ESPLICITI fra app autonome senza creare:
- shared database;
- account comune obbligatorio;
- continuous sync implicito;
- dipendenza da un provider cloud specifico;
- secondo dominio parallelo.

Il protocollo definisce:
- identità cross-app;
- ownership;
- envelope;
- provenance;
- revision;
- idempotenza;
- COPY/LINK;
- privacy boundary;
- media handoff descriptor;
- compatibility/versioning.

Il transport è separato dal protocollo.

======================================================================
2. SHARED ECOSYSTEM CORE v1 VS Life Bridge v1
======================================================================

SHARED ECOSYSTEM CORE v1
- è il protocollo canonico cross-app;
- possiede EcosystemEnvelope;
- possiede canonical app IDs;
- possiede bridgeId/idempotency semantics;
- possiede privacy/media/version contract;
- è transport-independent.

Life Bridge v1
- è una compatibility/product projection;
- adatta concetti di Journey/Memory/Moment/Diary alle entità del Core;
- può preservare compatibility con payload/identità storiche dove necessario;
- NON è un protocollo concorrente;
- NON deve ridefinire per i nuovi trasferimenti:
  - bridgeId canonico;
  - idempotency key;
  - app IDs;
  - schema/versioning del Core;
  - transport package;
  - ownership.

Regola:
nuove integrazioni cross-app devono parlare Shared Ecosystem Core v1.
Life Bridge resta projection/adapter di prodotto sopra il Core.

======================================================================


Gli app IDs wire sono stabili e NON devono essere sostituiti dal display name.

======================================================================
4. CANONICAL OWNERSHIP
======================================================================

Ogni entità resta canonica nell'app proprietaria.

Il Core distingue:
- source identity;
- canonical owner/provenance;
- destination materialization.

Un bridgeId NON sostituisce mai l'ID canonico locale.

COPY:
- la source resta owner dell'originale;
- il destinatario materializza una nuova entità locale indipendente;
- provenance della source viene conservata;
- revision future della source NON si applicano automaticamente.

LINK:
- canonical ownership resta alla source;
- il destinatario conserva una projection/reference esplicita;
- canonicalDeepLink è obbligatorio;
- non implica background sync;
- non implica accesso al database della source.

======================================================================
6. BRIDGE ID E IDEMPOTENZA
======================================================================

bridgeId canonico:

```text
ecosystem:v1:<ownerApp>:<ownerEntityType>:<ownerEntityId>
```

Esempio:

```text
ecosystem:v1:wonderlog:journey:journey-42
```

Il bridgeId:
- deriva dall'owner canonico/provenance;
- resta stabile fra revision;
- resta lo stesso fra COPY e LINK.

Idempotency key:

```text
<bridgeId>:<revision>:<transferMode>
```

Concettualmente:

```text
bridgeId + revision + transferMode
```

Esempio COPY:

```text
ecosystem:v1:wonderlog:journey:journey-42:1790929800000:copy
```

Esempio LINK:

```text
ecosystem:v1:wonderlog:journey:journey-42:1790929800000:link
```

Conseguenze obbligatorie:
- COPY e LINK sono delivery distinte;
- duplicate delivery della stessa key = NO DUPLICATE;
- duplicate concorrente = atomic/idempotent;
- nuova revision mantiene bridgeId e produce nuova idempotency key;
- revision stale non deve fare downgrade/mutazione silenziosa;
- una vecchia compatibility COPY key non deve sopprimere un LINK valido.

======================================================================
7. PROVENANCE OBBLIGATORIA
======================================================================

`EcosystemProvenance` deve preservare almeno:

```text
ownerApp
ownerEntityType
ownerEntityId
ownerRevision
canonicalDeepLink?
parentBridgeId?
```

Regole:
- provenance non viene sostituita silenziosamente dall'identità destination;
- revision rappresenta la source revision trasferita;
- LINK richiede canonicalDeepLink;
- eventuale re-share/derivazione usa parentBridgeId quando pertinente;
- provenance è parte del contratto, non metadata decorativa.

======================================================================
8. EXPLICIT SHARE E REVIEW PRIMA DELLA MATERIALIZZAZIONE
======================================================================

Cross-app transfer richiede:

```text
privacyScope = explicitShare
```

Pipeline destination canonica:

```text
RECEIVE PACKAGE
-> DECODE
-> VALIDATE VERSION
-> VALIDATE TARGET/CAPABILITY
-> VALIDATE EXPLICIT SHARE
-> VALIDATE MEDIA
-> CHECK IDEMPOTENCY/REVISION
-> SHOW EXPLICIT REVIEW
-> USER CONFIRMS COPY OR LINK
-> MATERIALIZE
-> RECORD DELIVERY/PROVENANCE
```

Regola:
la ricezione del package NON equivale a consenso alla materializzazione.

Transport/decode/validation failure:
NO DOMAIN MUTATION.

======================================================================
9. PROTOCOLLO != TRANSPORT
======================================================================

`EcosystemEnvelope` resta identico indipendentemente dal transport.

Transport possibili:
- local deep link;
- clipboard fallback;
- futuro cloud transport;
- altri adapter espliciti compatibili.

Il transport NON può ridefinire:
- ownership;
- bridgeId;
- COPY/LINK;
- revision;
- privacy;
- provenance.

Cloud transport, se introdotto, resta un adapter.
Auth/queue/retry/cursor/provider-specific logic NON entra nel Core contract.

Nessun continuous sync è implicito dal bridge.

======================================================================
13. MEDIA HANDOFF v1
======================================================================

Il modello generale supporta:

```text
omitted
shareToken
cloudObject
```

`omitted`
- metadata consentita;
- binary handoff assente intenzionalmente.

`shareToken`
- token obbligatorio;
- token può essere expiring/transport-specific;
- NON può contenere URI/path privati.

`cloudObject`
- locator safe obbligatorio;
- provider-specific;
- NON può essere file/local URI privato.

Private/local references vietate cross-app:

```text
file://
content://
media://
/data/
/private/
```

Stato certificazione attuale:
- Shared Core v1 MODELLA tutti e tre i tipi;
- Anna's Diary v1 certifica attualmente SOLO `omitted` per il binary handoff;
- Wonderlog v1 producer usa attualmente `omitted` per media binari;
- `shareToken` e `cloudObject` restano contract-valid ma NON certificati come
  binary handoff Anna v1.

Regola:
mai passare un URI privato solo perché funziona temporaneamente sul device.

======================================================================
14. VERSION / REVISION FAIL-SAFE
======================================================================

Schema/protocol:
- `schemaVersion != 1` -> reject;
- future/incompatible schema -> reject;
- no partial import.

Local transport:
- `transportVersion != 1` -> reject;
- no reinterpretazione silenziosa.

Revision:
- revision < 1 -> invalid;
- stale revision non deve sovrascrivere/downgradare uno stato più nuovo;
- nuova revision valida può essere trattata come nuova delivery;
- policy di materializzazione resta destination-owned.

Malformed required field / enum / date / target:
- fail closed;
- stable error surface;
- NO domain mutation.

```text

```

```text

content://
media://
/data/
/private/
```

Expected:
- private/local media reference -> reject;
- safe omitted media -> metadata-only transfer;
- no domain mutation on invalid media package.

VECTOR E — FAIL CLOSED

Reject without domain mutation:
- schemaVersion != 1;
- transportVersion != 1;
- privacyScope != explicitShare;
- LINK without canonicalDeepLink;
- invalid/private media locator;
- missing shareToken token;
- missing cloudObject locator;
- wrong target / unsupported capability;
- malformed required package fields.

19. CRITERI PER FUTURE APP
======================================================================

Una nuova app dell'ecosistema deve:
- ottenere un canonical app ID stabile;
- registrare scheme/capability nel registry;
- usare EcosystemEnvelope v1 senza fork;
- produrre/consumare Golden vectors pertinenti;
- non introdurre un protocollo parallelo;
- usare projection adapter di dominio se il proprio modello differisce;
- mantenere protocol/transport separati;
- rispettare explicitShare e private-media boundary.

Nessuna nuova feature di prodotto è implicata da questo Golden.
