1. SCOPO
Standardizzare la personalizzazione di app ricche di moduli senza creare nuovi
owner di dati e senza confondere "nascondere" con "disabilitare/cancellare".

Regola centrale:
VISIBILITY != OWNERSHIP != PERSISTENCE.

Un modulo nascosto non perde dati, non cambia canonical ownership e resta
riattivabile.

2. PRESENTATION-ONLY CONTRACT
Il flag controlla soltanto discoverability, navigation, presentation e ordering.
NON controlla delete/purge, database ownership, backup ownership, sync ownership
o entitlement ownership.

3. REUSE EXISTING STATE OWNER
Preferire l'owner di preferenze già canonico.
NO secondo preferences store, router, database o sync queue.

4. PRESET + CUSTOM MODEL
Pattern candidato:
ESSENTIAL
DOMAIN_PRESET
COMPLETE
CUSTOM

Requisiti:
- preset deterministici e reversibili;
- toggle manuale -> CUSTOM;
- restore complete sempre disponibile;
- dependency closure deterministica.

5. BACKWARD COMPATIBILITY
Profilo legacy senza nuovi campi -> esperienza precedente completa.
Campi futuri sconosciuti: ignorare fail-safe quando possibile.

6. MODULE DEPENDENCIES
Se A richiede B:
A ON -> B ON
B OFF -> A OFF
La normalizzazione vive nel preference/domain contract, non nei widget.
Donor example: Cycle Tracker -> Private Vault.

7. ONBOARDING ATOMICITY
SELECT PRESET -> COMPLETE ONBOARDING -> persist preset + completion atomically.
Un first run interrotto non lascia personalizzazione mezza applicata.
Integrare con GOLDEN_ONBOARDING_FIRST_RUN_FLUTTER_v1_DRAFT.txt.

8. PROGRESSIVE DISCLOSURE
Feature avanzate possono esistere senza occupare la superficie primaria.
Stato tecnico healthy può restare quiet; error/degraded/pending anomalo deve
riemergere.
QUIET HEALTHY STATE > PERMANENT SUCCESS BADGE.

9. CORE REACHABILITY
Personalizzazione non deve rendere irraggiungibili:
- data safety/recovery;
- account/privacy;
- Search quando core;
- impostazioni per riattivare moduli;
- dati già posseduti.

10. BACKUP / ACCOUNT / RESTORE
Le preferenze seguono il lifecycle canonico. Definire replace, merge, account
switch e legacy defaults. Hidden module non muta domain data.

11. ENTITLEMENT BOUNDARY
MODULE ENABLED != ENTITLED.
Il diritto d'accesso resta nel Golden Entitlement/provider pertinente.
